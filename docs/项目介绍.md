# 农餐馆 · 农大智慧餐厅

## 一句话

把食堂窗口的「现场菜单」数字化，叠加可换算的营养参考、同学众包的实时排队和真实点评，回答每天中午最难的两个问题：**吃什么、去哪里吃。**

## 问题：不是没得吃，是看不见

- **菜单只在灯箱上。** 窗口今天卖什么、多少钱、几点收摊，只有走到跟前才知道。线上没有任何一份可检索的菜单。
- **营养只在个别窗口公示。** 公一食堂 18 号窗口（低脂美食新风尚）贴了每 100 克的营养表，但学生要站在窗口前逐行读；其余窗口完全没有数据。
- **排队全靠目测。** 中午 12:00 的食堂，哪个窗口人多、要等几分钟，只能靠走廊里看一眼，走到窗口才发现排错队。
- **点评只在私聊里。** “哪个菜好吃”停留在同学之间的口头推荐，没有沉淀，也不按菜品聚合。

这三件事其实是同一个决策链：**去哪吃 → 吃什么 → 值不值。** 分散的信息导致每一步都在重新试错。

## 方案：把一条决策链放进一个页面

「农餐馆」以**窗口**为单位组织信息，而不是以食堂或菜品为单位——因为学生实际做选择时，先看窗口排不排队，再看这个窗口有什么菜。

1. **菜品与营养**
   6 个窗口、43 道菜，每道菜有价格、参考份量、每 100g 的热量 / 蛋白质 / 脂肪 / 碳水 / 膳食纤维。用户可选半份、标准份、1.5 份，营养按份量实时换算。
   18 号窗口的数值录入自现场公示表；其余窗口是 AI 估算。每张卡右上角标明来源，详情页写清「不是检测报告」。

2. **共享排队雷达**
   学生在窗口前点「报一下排队」，选择人数（0–30）。服务端取最近 20 分钟内最多 5 条上报的**中位数**，折算预计等待分钟数（每人约 0.4 分钟）。
   时间窗抗噪：20 分钟没有新数据就标灰“待更新”，而不是继续展示过时数字。同一设备同一窗口 3 分钟内只能报一次，抑制刷数据。

3. **真实点评**
   1–5 星 + 200 字，按菜品聚合平均分和点评数，标注相对时间。同一设备 24 小时内再次点评会覆盖旧评，避免同一个人反复刷分。

4. **智能配餐**
   按均衡 / 健身高蛋白 / 减脂轻盈 / 清爽素食四个目标，从真实菜品里配一餐（主菜 + 主食 + 蔬菜），并把**窗口排队状态纳入排序**：同样满足营养目标时，优先推荐当前不排队的窗口。可整餐加入「今日餐盘」。

5. **今日餐盘与现场相册**
   餐盘汇总本餐热量与三大营养素；14 张 2026-11-21 的现场实拍可以逐张查看，菜名和价格能回溯到照片。

## 为什么是它：三个不一样

- **信息可溯源。** 大多数校园餐饮工具给一个孤零零的热量数字。我们把「窗口公示」和「AI 估算」分开标记，并保留现场照片；用户知道每个数字从哪来，也知道它有多可靠。
- **排队以窗口为单位、以时间窗为单位。** 没有做“餐厅拥挤度”这种模糊指标，而是具体到“18 号窗口前面 10 个人，约 4 分钟，刚刚更新”。众包数据的可信度靠时间衰减和多重上报的中位数保证。
- **推荐把排队算进去。** 配餐不是随机抽菜，而是在满足营养目标的前提下，主动避开正在排队的窗口——把“吃什么”和“去哪吃”合成一个动作。

## 技术实现

- 后端：单文件 Node.js 服务（`server.js`），**零第三方依赖**，只用 `http / fs / path / crypto`。静态资源、REST API、JSON 存储合一。
- 数据：`data/menu.json` 是唯一菜品源；运行期点评与排队写入 `data/db.json`，采用临时文件 + rename 的原子写，写入串行化。
- 前端：原生 HTML / CSS / JavaScript，无框架、无构建、无 CDN，断网可完整演示。
- 安全：路径穿越校验、请求体 256KB 上限、输入长度裁剪、所有用户文本转义后渲染、上报与点评双重限流。
- 客户端：网页版（原生 HTML/CSS/JS），外加一套原生微信小程序（`miniprogram/`），两者共用同一套后端与同一份排队 / 点评数据。小程序包含食堂选择（未录入食堂显示「待录入」且不可选）、排队雷达、目标配餐、好评榜、点评点赞与碳排粗估。
- 验收：`tools/e2e.js` 用无头 Edge 走真实浏览器，覆盖菜单渲染、搜索、点评发布、排队上报、配餐加入餐盘等 12 项断言；小程序通过 JS / JSON / WXML 静态校验。

## 边界与诚实说明

- 目前只有公一食堂（公寓一食堂）上线；公二、公三食堂标记为“待录入”，不做虚假填充。
- 除 18 号窗口外，营养数值是 AI 估算，会随配方、用油和份量变化，仅作日常饮食参考，不构成营养或医疗建议。
- 没有账号体系：用浏览器本地生成的设备标识做点评归属和限流，换设备即视为新用户。
- 点评与排队初始为空，由真实使用产生；演示时不预置假数据。
